# V3.3｜四类核心协议冻结与兼容迁移规范

> **定位**：用于 PR-02 开始前完成语义冻结，供 PR-02/02B/03/06/07/08 共用。表内“冻结”指外部语义、安全不变量、字段用途和错误处理固定；后续允许向后兼容地增字段。以下是设计规范，当前仓库部分模型已存在，不要原样再造第二套类。
>
> **当前读取的代码事实**：`domain/agent_protocols.py` 有 `TaskRecord`, `PlanDecision`, `AgentResult`, `StatePatch`；`domain/state.py` 有 `DesignState.task_plan`；`domain/proposals.py` 有 `ParameterChangeProposal`, `ProposalResolution`；`domain/enums.py` 有 `TaskStatus`, `PrecheckStatus`, `SimulationStatus`；`core/dependency_tracker.py` 把 `TaskRecord.dependencies` 当字段依赖；`domain/write_context.py` 有受信 `WriteContext`，并非真正 Web 用户认证。实现前再次核对 main。

## A. 动作/规划/守卫/执行结果协议（PR-02 冻结）

### A1. 单一 ActionCatalog（权限源不是 LLM）

建议 `ActionSpec`：

```python
class ActionSpec(BaseModel):
    action: str                  # 唯一规范名
    executor_id: str             # 具体专业 Agent / 确定性工具 / unavailable_stub
    required_input_refs: tuple[str, ...] = ()
    required_gate: str | None = None
    output_schema_id: str
    write_effect_class: str      # READ_ONLY / DOMAIN_PATCH / HUMAN_DECISION
    requires_human: bool = False
    supported: bool = True
    action_version: str = 'v1'
```

`selected_agent` 不应成为 Planner 可自由伪造的权限；Guard 检查 `action` 与目录中的 `executor_id` 一致，并检查前置条件、权限、允许写入范围、当前可用性与版本。`ActionSpec` 是**应用受信配置**，不能从知识检索结果直接载入高权限动作。

### A2. 兼容现有 PlanDecision

**现有字段必须保留**：`action`, `selected_agent`, `input_refs`, `rationale`, `expected_result`, `requires_confirmation`, `state_version`。**可最小增量补充** `decision_id`、`task_id`、`plan_revision`、`catalog_version`、`output_schema_version`、`observed_input_hash`；不要因为“架构更漂亮”而重命名原有字段。

构成有效决策：基于指定权威 `state_version`，引用当前 `ActionSpec` 能力，明示所用 input refs、预期结果和可解释的简短原因。**JSON Schema 校验通过只说明格式正确，不表示授权通过。**

`LLMPlanner` 可提出一个合法动作或一个有限近期计划；若非法动作、未注册 Agent、输入版本过期或需要 USER 授权，Guard 阻止而不是执行。与状态无关的连续无效输出最多有限次重试并停止。

### A3. GuardDecision（建议新增小模型）

| 字段 | 类型 | 含义 |
|---|---|---|
| `decision_id` | str | 关联原始 PlanDecision |
| `verdict` | `ALLOW/NEEDS_USER/BLOCK` | 只有 ALLOW 才可执行领域动作 |
| `reason_code` | str | 稳定机器可识别的原因（如 STALE_VERSION / INPUT_NOT_READY / UNSUPPORTED_ACTION / PERMISSION_DENIED / RULE_UNAPPROVED） |
| `required_input_refs` | list[str] | 阻断时明确缺什么 |
| `observed_domain_version` | int | 检查实际面对的状态版本 |
| `action_spec_version` | str | 该动作规则版本 |

`NEEDS_USER` 只能生成受信用户确认请求，不能把它当成“用户已批准”。若请求的业务对象不存在/过期，返回 BLOCK 或过期事件并重新观察。

### A4. 兼容现有 AgentResult

**现有字段保留**：`task_id`, `status`, `state_patch`, `issues`, `suggested_next_actions`, `evidence_refs`。新增 `operation_id`、`base_state_version`、`output_schema_version`、`produced_artifact_refs` 可以放进安全 envelope/执行记录，无需强行扩展每个专业 Agent 模型。

- `status=SUCCESS` 表示 Agent 按协议完成调用，不代表轴承校核 PASS。
- `AgentResult.state_patch` 只能作为建议，统一经 `ResultValidator` 校验后用 `WriteContext(AGENT)` 提交。
- `evidence_refs` 应是指向 SourceCatalog/可信用户消息/确定性计算记录的结构化引用，不能自封审批来源。
- 真实 RuleEngine 出具的受信校核结论必须通过单独 SYSTEM/校核签名路径写回，不能凭任意 AgentResult 直接写预校核通过状态。

### A5. TaskPlan 的最小规划承诺

PR-01 `DesignState.task_plan` 是**唯一持久任务记录**；`TaskPlanView` 是只读投影，加入目标、plan_revision 和 replan_reason，不能新建第二套业务 TaskRecord 列表。第一版计划 1–3 步即可，重要的是状态变化可使后继任务重新规划、且 trace 保存原因。

## B. 用户交互事件与确认（PR-02 冻结语义，PR-03 实现）

### B1. 共用可信输入信封 `TrustedUserEventEnvelope`

```json
{
  "event_id": "evt-uuid",
  "design_id": "design-uuid",
  "kind": "USER_TURN",
  "actor_id": "trusted-user-session",
  "source_message_id": "msg-uuid",
  "target_id": null,
  "target_revision": null,
  "expected_domain_version": 12,
  "payload_schema_version": "1",
  "received_at": "ISO8601"
}
```

`actor_id`、消息引用和时间均由**可信服务层**附加；Agent 输出中的同名字段不起权限作用。PR-02 离线 harness 可以有“可信假用户”适配器，但不能让 Agent 伪造 USER context。后续 API 登录鉴权另行实现，不要将本信封等同于密码学身份认证。

### B2. 六类事件与映射

| 名称 | 产生条件 | 处理与持久结果 | 禁止误用 |
|---|---|---|---|
| `UserTurn` | 用户提交自然语言/附件 | 保存消息与 evidence ref；由 LLM 提出信息抽取提案 | 原文文本中“确认”二字不自动授权任何参数 |
| `UserCorrection` | 用户明确纠正某个旧字段 | 绑定旧 revision、新证据；可信写入；关联结果 STALE | 不允许随便指定未存在的源消息 ID |
| `UserConfirmation` | 用户按明确确认动作接受候选/参数某版本 | 附目标 id/version、当前范围/未验证项摘要和确认请求 ID；进入受信提交 | 老候选或老规则下的确认不能沿用 |
| `UserRejection` | 用户明确拒绝建议/候选/参数变更 | 记录拒绝事件与对象版本；当前权威参数原值不变 | 不应该以“无参数变化”为由丢失审计 |
| `ParameterChangeProposal` | 建议改已确认值 | 复用 PR-01 模型：`proposal_id, parameter_id, base_revision, proposed_record, reason, status` | 不写入 parameters，除非用户显式批准 |
| `ConfirmationExpired` | 确认请求创建后目标或关键依赖发生变化 | 将旧请求标过期，需刷新展示与用户授权 | 不因命令被重放而再确认旧版本 |

**实现建议**：上述六种可以作为 typed application events / commands，共用 envelope，在 PR-01 现有 `StateEvent`/`ParameterChangeProposal` 上关联审计信息；不是要求必须新增六张表或六个 Pydantic 顶级持久模型。特别是对普通 UserTurn 的自然语言“我接受”，若无明确的待确认目标和可验证对话交互上下文，须澄清所接受对象，而不是自动升级权限。

### B3. 确认失效范围

确认请求带 `target_kind`, `target_id`, `target_revision`, `candidate_dependency_digest`, `rule_set_version`, `confirmation_request_id`。**V1 最保守实现**：域状态版本变化时重检目标与关键依赖，相关字段变化则失效；若无法证明无关，先失效而不是放行。并非每次无关聊天都要过期，后续 PR-07 可凭精确 dependency digest 减少误失效。

## C. 两类依赖（PR-02 固定语义，PR-07 精准追踪）

**发现的代码冲突**：已有 `TaskRecord.dependencies: list[str]`；`DependencyTracker` 把它当改变的“字段 ID”集合；如果未来同时存 `t-001` 和 `journal_diameter`，失效算法会混淆。

| 概念 | 冻结字段名 | 存什么 | 作用 |
|---|---|---|---|
| 任务前置关系 | `depends_on_task_ids` | `task:t-001` / 纯任务 ID（统一选一种） | 当前执行必须等待哪些任务成功完成 |
| 数据消费关系 | `consumed_input_refs` | `parameter:journal_diameter@rev2`, `constraint:width_limit@rev1`, `case:nominal@rev1`, `rule_set@v1`（结构可用 typed refs） | 变化后哪些任务、候选/预校核需要 STALE |

**推荐兼容实现**：本 PR 先将旧 `dependencies` 定义为 *legacy field consumed dependencies*；必要时新增两组显式字段并提供只读兼容转换，不静默重新解释旧存量为任务依赖。新增字段后 `DependencyTracker` 只对数据依赖失效，调度器只对任务前置关系建图。旧数据无法确认语义时标记需要人工迁移或保守失效。禁止将前置任务 ID 当工程字段比较。

**无精确依赖时的准则**：宁可旧结果多变 STALE、增加重算，也不能漏掉已失效的 PRECHECK_PASS。`CandidateDesign.source_parameter_revisions` 当前保存的可能是所有参数的保守快照，PR-07 才升级为经工具记录的真实 consumed refs，且必须测试间接派生依赖传播。

## D. 四个容易混淆的状态和另外两类状态（PR-02 冻结含义）

**禁止把所有结果状态塞进一个通用 Enum**；沿用 PR-01 各自枚举：

| 常量 | 属于哪种当前枚举 | 含义 | 不能据此推断 |
|---|---|---|---|
| `NOT_AVAILABLE` | `SimulationStatus` | 当前没有真实可调用 DLAP | 不等于求解失败或膜厚不合格 |
| `NOT_EVALUATED` | `PrecheckStatus` / `SimulationStatus` | 对相应对象还没有执行该类检查 | 不等于已经通过，也不等于明确失败 |
| `REVIEW_REQUIRED` | `PrecheckStatus` | 规则冲突、必需证据/审批缺失、无法给受信结论 | 不等于违反工程约束的 FAIL |
| `PRECHECK_PASS` | `PrecheckStatus` | 当前指定输入与候选版本、适用的必检规则均已实际评价且通过，覆盖证明有效 | 不等于仿真、可靠性、完整轴承合格 |
| `PRECHECK_FAIL` | `PrecheckStatus` | 至少一项适用的已执行必检规则明确违反 | 不等于工具执行失败 |
| `STALE` | `PrecheckStatus` 等关联对象 | 旧结果对应输入/规则/候选已变化，不能用作当前 PASS | 不等于历史结果被删除 |

另应区分 `TaskStatus.COMPLETED`（动作完成，可能给出工程 FAIL）和 `AgentResultStatus.SUCCESS`（该 Agent 处理调用成功）。

### D1. RuleCoverageSpec 校验

```yaml
coverage_id: cyl_v1_rules
scope: cylindrical_radial_hydrodynamic_single_steady
required_when_applicable:
  - input_units_and_validity
  - user_fixed_constraints_preserved
  - installation_width_limit_if_present
  - material_allowlist_if_present
conditional_approved_rules:
  - approved_mean_pressure_rule_if_applicable
explicitly_unverified:
  - true_minimum_film_thickness
  - max_oil_temperature
  - local_film_peak_pressure
```

覆盖定义须存在并获软件流程校验、必检集合不能因为引擎没加载到规则就默认全空 PASS；适用项目若缺输入、版本过期或规则未获审核，应返回 `REVIEW_REQUIRED`/`NOT_EVALUATED`；非适用项应明确标 `NOT_APPLICABLE` 的逐项判定，不得将它们算作 PASS。`PRECHECK_PASS` 仍需明确附带“仅对已覆盖的预检查项目而言”。

## E. 兼容性发布/冻结检查表

1. 当前 PR-01 schema 反序列化旧 JSON 仍能运行；新增枚举或字段明确兼容默认值和迁移。
2. 同一操作重复调用不重复更新 `DesignState.state_version`/候选/确认/`StateEvent`。
3. Guard 能拦截假源消息 ID、假 user 角色、过期 state_version、非法 action、不可用 simulation。
4. 非法/过期确认不修改旧参数；拒绝操作可审计且不覆盖现值。
5. 数据依赖变更、规则版本变更使旧 PASS STALE；前置任务 ID 不参与字段依赖判定。
6. 模型输出的 `source` / `actor` / `confirmed_by` / `approval` 不具有权威效力。
7. Schema 审查前保留变更兼容说明；冻结后版本号按 `protocol_version` 演进。
